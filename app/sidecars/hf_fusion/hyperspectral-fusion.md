# HyperFusion Hyperspectral Fusion Pipeline

## Purpose

This document explains the current HyperFusion dual-camera fusion method in plain technical language. The goal is to combine data from the FX10e camera and the SWIR3 camera into one registered hyperspectral result per detected object.

The FX10e camera is used as the spatial reference. SWIR3 data is resampled, shifted, and refined so that it lands on the FX10e pixel grid. After alignment, the pipeline keeps the lower-wavelength bands from FX10e and the higher-wavelength bands from SWIR3.

In short:

```text
capture -> preprocessing -> GSAM segmentation -> coarse alignment -> phase correction -> spectral stitching
```

## Where It Runs

The fusion code lives under:

```text
resources/hf_fusion/
```

The main entry points are:

- `fusion_cli.py`: command-line entry used by the C++ app.
- `src/hf_fusion_pipeline.py`: pipeline coordinator.
- `src/coarse_alignment.py`: spatial coarse alignment.
- `src/phase_correction.py`: fine alignment using shared wavelength bands.
- `src/spectral_fusion.py`: final spectral stitching and ENVI output.

The app runs the Python pipeline as a one-shot subprocess after preprocessing and segmentation are complete.

## Required Inputs

For each session and illumination mode, the pipeline expects both cameras:

```text
{session}/{mode}/fx10e/
{session}/{mode}/swir3/
```

where `{mode}` is usually:

```text
reflectance
transmittance
```

Each camera folder must contain preprocessed products:

```text
{session}/{mode}/{camera}/preprocessed/
  *_rgb.png
  *_ffc.hdr
  *_ffc.raw
  segmentation/
    segmentation_results.json
    masks/
      mask_001.png / mask_001.npy
      mask_002.png / mask_002.npy
      ...
```

These files are generated by the capture post-processing step:

- Dark and white reference correction.
- Flat-field corrected hyperspectral cube (`*_ffc.hdr` / `*_ffc.raw`).
- RGB preview image (`*_rgb.png`).
- GSAM2 object segmentation masks.

Fusion currently requires the same number of segmented objects in FX10e and SWIR3 for each illumination mode.

## Calibration Used

Spatial calibration comes from `app/preset/hyperfusion.cfg`.

Current values:

```ini
fx10e_spatial_mm_per_pixel = 0.21
swir3_spatial_mm_per_pixel = 0.51
fusion_margin_mm = 5.0
```

The FX10e grid is finer, so SWIR3 is upsampled onto the FX10e grid.

The current SWIR-to-FX spatial scale is:

```text
scale = swir3_mm_per_pixel / fx10e_mm_per_pixel
      = 0.51 / 0.21
      = 2.43x
```

That means a SWIR3 image of width `W` and height `H` is resized to approximately:

```text
target_width  = round(W * 2.43)
target_height = round(H * 2.43)
```

## Pipeline Overview

The pipeline has three main stages.

```text
Stage 1: Coarse alignment
Stage 2: Phase correction
Stage 3: Spectral fusion
```

Each stage works per detected object, also called an ROI.

## Stage 1: Coarse Alignment

The purpose of coarse alignment is to place SWIR3 data onto the FX10e coordinate system using spatial calibration and object masks.

### 1. Load FX10e Data

The pipeline loads:

- FX10e RGB preview image.
- FX10e segmentation masks.
- FX10e flat-field corrected hyperspectral cube.

FX10e stays at native resolution and becomes the reference grid.

### 2. Upsample SWIR3 to the FX10e Grid

SWIR3 has larger pixels than FX10e, so SWIR3 data is resized to match the FX10e physical ground scale.

Different data types use different interpolation methods:

- SWIR3 RGB preview: bicubic interpolation by default.
- SWIR3 masks: nearest-neighbor interpolation.
- SWIR3 hyperspectral cube: bilinear interpolation, band by band.

The mask uses nearest-neighbor interpolation because masks are labels, not continuous image intensity. This prevents blurred or fractional mask edges from creating invalid labels.

The hyperspectral cube uses bilinear interpolation because reflectance/transmittance values are continuous image values.

### 3. Compute Object Centroids

For every GSAM mask, the pipeline computes the centroid from all foreground pixels:

```text
cx_px = mean(x positions where mask > 0)
cy_px = mean(y positions where mask > 0)
```

Then it converts pixels to millimetres:

```text
cx_mm = cx_px * mm_per_pixel
cy_mm = cy_px * mm_per_pixel
```

After SWIR3 masks are upsampled, their centroids are measured on the FX10e grid.

### 4. Match FX10e ROIs to SWIR3 ROIs

The current matching method is simple and deterministic:

```text
sort FX10e objects left-to-right
sort SWIR3 objects left-to-right
pair object 1 with object 1
pair object 2 with object 2
...
```

Important detail: GSAM ROI labels are not treated as spatial order. `roi_001` does not necessarily mean the leftmost object. GSAM assigns labels in detection order, which may be confidence order or model output order. The fusion pipeline pairs objects by centroid position, not by ROI label number.

The app rejects the run if:

- FX10e and SWIR3 have different ROI counts.
- A paired centroid distance is too large.

The current maximum pair distance is:

```text
max_pair_distance_mm = 50.0
```

### 5. Compute the Coarse Shift

For each matched pair:

```text
dx_mm = fx_centroid_x_mm - swir_centroid_x_mm
dy_mm = fx_centroid_y_mm - swir_centroid_y_mm
```

This millimetre shift is converted to FX10e pixels:

```text
dx_px = dx_mm / fx10e_mm_per_pixel
dy_px = dy_mm / fx10e_mm_per_pixel
```

This shift moves the SWIR3 data onto the FX10e canvas.

### 6. Crop the Object Region

For each matched object, the pipeline computes a crop around:

- the FX10e mask
- the shifted SWIR3 mask

It takes the bounding box around both masks, then expands it by `fusion_margin_mm`.

Current margin:

```text
fusion_margin_mm = 5.0
margin_px = ceil(5.0 / 0.21) = 24 pixels
```

The crop is clamped to the valid overlapping field of view between FX10e and upsampled SWIR3.

### 7. Produce Coarse Alignment QA

The pipeline saves a per-ROI RGB overlay so the user can inspect whether the coarse placement looks reasonable.

## Stage 2: Phase Correction

The purpose of phase correction is to refine the alignment after coarse centroid matching. Coarse alignment gets SWIR3 close; phase correction estimates a smaller sub-pixel correction using image texture in wavelength bands shared by both cameras.

One-sentence summary:

```text
Use the shared wavebands to run phase correlation on chip-mask regions, estimate a sub-pixel translation and optional small scale correction, then warp the SWIR3 cube onto the FX10e crop.
```

### 1. Select Shared Wavelength Bands

The default phase-correction wavelength window is:

```text
wl_min = 977.0 nm
wl_max = 990.0 nm
```

The pipeline looks for FX10e bands in this range and pairs each one with the nearest SWIR3 band. A band pair is accepted only if the wavelength difference is small enough:

```text
max_pair_delta_nm = 8.0
```

### 2. Build the Phase-Correlation Mask

The phase-correlation region is based on the object masks:

```text
pc_mask = FX10e mask OR shifted SWIR3 mask
```

The mask is dilated to include some boundary and nearby signal:

```text
mask_dilate_px = 8
```

The default minimum usable mask size is:

```text
min_masked_pixels = 500
```

### 3. Normalize Each Band Inside the Mask

For every paired wavelength band, each image is normalized inside the mask:

```text
normalized = (value - mean_inside_mask) / std_inside_mask
```

Pixels outside the mask are set to zero. This makes phase correlation focus on relative spatial pattern rather than absolute brightness differences between cameras.

### 4. Estimate Translation with Phase Correlation

The pipeline uses OpenCV phase correlation:

```text
cv2.phaseCorrelate(FX_band, SWIR_band, mask)
```

For each paired band, this returns:

```text
dx_px
dy_px
response
```

The final correction is the median over all valid band pairs:

```text
final_dx = median(dx values)
final_dy = median(dy values)
final_response = median(response values)
```

The correction is accepted only if:

```text
final_response >= 0.25
```

If the correction is larger than expected, it is capped:

```text
refine_cap_px = 3.0
```

### 5. Optional Scale Search

Scale refinement is currently enabled:

```text
scale_refine = true
scale_search_min = 0.985
scale_search_max = 1.015
scale_search_steps = 15
scale_cap = 0.02
```

For each shared band pair, the pipeline tries 15 uniform scale values from `0.985` to `1.015`. For each candidate scale, it scales the SWIR3 band around the object-mask centroid, runs phase correlation, and keeps the best response.

The final scale is the median of the best scales across band pairs. The result is capped to within 2% of no scaling.

### 6. Warp SWIR3 After Refinement

If phase correction is accepted:

- SWIR3 HSI cube is warped with bilinear interpolation.
- SWIR3 mask is warped with nearest-neighbor interpolation.
- The refined mask overlap is measured and written to metadata.

## Stage 3: Spectral Fusion

The purpose of spectral fusion is to create one hyperspectral cube from the aligned FX10e and SWIR3 ROI cubes.

The current method is spectral stitching, not spectral blending.

Default split:

```text
spectral_split_nm = 1000.0
```

Fusion rule:

```text
use FX10e bands where wavelength <= 1000 nm
use SWIR3 bands where wavelength > 1000 nm
concatenate the bands along the spectral axis
```

The spatial shape of the two ROI cubes must match before stitching. If the shapes differ, fusion fails instead of writing a misleading output.

The fused cube is saved as ENVI BIL float data:

```text
roi_NNN_fx10e_swir3.raw
roi_NNN_fx10e_swir3.hdr
```

## ROI Mask for Spectra

For exported ROI spectra, the default fused mask is:

```text
roi_mask_mode = intersection
```

That means spectra are calculated only from pixels that are inside both:

- the FX10e mask
- the refined SWIR3 mask

This avoids using pixels where only one camera sees the object.

The most important metadata file is:

```text

```

It records:

- session and mode
- reference camera
- spatial scale
- FOV intersection
- ROI pairs
- coarse shifts
- phase-correction result
- overlap metrics
- fused output file paths

## App Workflow

From the app, fusion can run in two ways:

1. Automatically after a scan, if preprocessing, GSAM segmentation, and spectral fusion are enabled.
2. Manually with `Run fusion on session...`.

If a selected session is missing `preprocessed/` outputs, the app can run preprocessing and GSAM first, then start fusion.

The command-line equivalent is:

```powershell
cd resources\hf_fusion
.\.venv\Scripts\Activate.ps1
python fusion_cli.py --session E:\chiptest --mode reflectance
```

For the Python environment:

```powershell
cd resources\hf_fusion
.\setup_venv.ps1
```

The app always uses `resources/hf_fusion/` (code + `.venv`).

## Practical Interpretation

The pipeline is object-aware. It does not try to globally align the whole FX10e image and the whole SWIR3 image with one transform. Instead, it aligns each detected chip separately.

This is useful because:

- each chip gets its own crop
- each chip gets its own shift estimate
- local alignment errors are easier to inspect
- each fused ROI produces its own cube and spectrum

The main assumption is that GSAM detects the same physical chips in both cameras. ROI label numbers do not need to match spatial order, but the object counts and left-to-right object order should correspond between cameras.

## Current Limitations

- ROI matching is left-to-right sorting, not a full assignment algorithm such as Hungarian matching.
- Fusion uses a hard wavelength split, not weighted blending in the overlap region.
- Phase correction depends on usable signal in the shared 977-990 nm band range.
- The pipeline expects segmentation masks to be reliable; poor masks can create poor crops or bad phase-correction regions.
- The current output is per ROI, not one full-scene fused mosaic.

## Summary

HyperFusion fusion takes preprocessed FX10e and SWIR3 data, uses GSAM masks to find the same object in both cameras, resamples SWIR3 onto the FX10e grid, performs coarse centroid alignment, refines the result with shared-waveband phase correlation, and finally stitches FX10e and SWIR3 spectral bands into one fused ENVI cube per object.
